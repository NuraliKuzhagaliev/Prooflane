## E1 — medium / reliability / open

**Место:** `prooflane/app.py:230`, вызов `sandbox.run` на строке 242; обработчик `SandboxError` вне цикла на строке 276.

**Триггер:** первая сгенерированная программа превышает timeout, но контейнер подтверждённо удалён (`cleanup=true`). Sandbox поднимает `SandboxError` с метаданными исполнения. Вторая сгенерированная программа могла бы пройти.

**Следствие:** run сразу завершается failed; предусмотренная в live-цикле вторая попытка и repair feedback не используются. Для обычного JSON/contract mismatch повторная попытка работает, но не для этой ошибки исполнения. Данные не выдаются как проверенные; дефект ограничен восстановлением после сбоя.

**Воспроизведение:** `engineering_probe.py`, case `timeout_then_success`; FakeSandbox вызывает настоящую ветку обработки API, сначала возвращает исключение с cleanup=true, при втором вызове вернул бы правильный контракт. Результат в `engineering-probes.json`: HTTP 200, `status=failed`, `provider_calls=1`, `sandbox_calls=1`, `stored_runs=1`. Уверенность высокая; это проверка оркестрации, не настоящий timeout Docker.

**Минимальная коррекция:** внутри цикла сохранять неудачную попытку и разрешать оставшуюся попытку после безопасно очищенного, допускающего повтор сбоя исполнения. Ошибки контейнерной изоляции, cleanup=false или неизвестный cleanup должны немедленно останавливать run; провайдер/инфраструктуру не надо слепо повторять.

**Acceptance:** тот же сценарий даёт две попытки и verified; обе попытки сохранены, первая содержит ошибку и cleanup=true. Контроль cleanup=false/отсутствует не делает второй вызов и сохраняет карантинное поведение. Режим sandbox без модели остаётся одноразовым.

## Продуктовые ограничения и seam для сценариев

Это не дополнительные дефекты: квоты в памяти процесса сбрасываются при рестарте; cookie является границей анонимной сессии, а не учётной записью; Docker group означает доступ к привилегированному daemon; JSON receipt не аутентифицирует автора/факт реального исполнения. Эти ограничения уже согласуются с документацией и должны остаться явными. AI генерирует реализацию фиксированного арифметического контракта; свободный вопрос не превращает продукт в произвольный финансовый аналитик.

Для нового сравнения baseline→scenario существенны следующие acceptance-гейты:

1. Оба runs проверены на владение текущей сессией; исходный baseline не изменяется. Сценарий привязан к hash полного baseline receipt и конкретным исходным строкам.
2. Не более 10 разрешённых cell edits; отклоняются повторные/конфликтующие пары row/field, неизвестные поля, невалидные money/quantity, ложные from-values. Смена vendor/notes/invoice_id и любые незаявленные изменения отклоняются standalone verifier.
3. Signed Decimal deltas независимо пересчитываются из обоих CSV. Отрицательная разница не маркируется как фактически возвращённые деньги; отрицательные строковые variances не netting-уются с положительными.
4. Receipt bundle содержит оба полных inputs/receipts и проверяется после истечения серверной истории. Пересчитанные hashes не должны позволять скрытно менять ячейки вне заявленного patch или подменять parent relation.
5. Scenario идёт через тот же валидатор/режим/квоты/изолированный runtime. Mode явно показан; live по-прежнему требует operator token. Reference-сценарий не изображается результатом AI.

Это направления проверки нового кода, а не заключение о пока разрабатываемой реализации.
