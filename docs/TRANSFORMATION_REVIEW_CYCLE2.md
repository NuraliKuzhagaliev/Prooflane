## Найденные дефекты

### C2-1 — P2: отпечаток запроса не учитывал присутствие полей

- Место: `prooflane/case_api.py`, `execute_operation` (около строки 139) и `create_work`.
- Триггер: успешно создать кейс из существующего baseline с `{name,baseline_run_id,request_id}`, затем повторить тот же ID, добавив явное `mode:"reference"`.
- Воспроизведение до исправления: первый запрос **200**, изменённая форма с тем же ID **200**, такая же изменённая форма с новым ID **422**. `model_dump` давал одинаковый отпечаток для отсутствующего поля и явного default, хотя `create_work` различает их через `model_fields_set`.
- Последствие: контракт «изменённый запрос с тем же ID отклоняется» нарушался; replay обходил проверку смешанной формы ввода. Нового исполнения или утечки данных в пробе не наблюдалось.
- Минимальная коррекция: включить в отпечаток имена реально переданных полей, исключив технический `request_id` и не сохраняемый operator token, либо проверять форму до replay.
- Статус: **FIXED, повторно PASS**. Основной агент изменил отпечаток на `payload + sorted(model_fields_set - {operator_token,request_id})`. Независимый повтор дал **200** для первого запроса, **200** для неизменённого replay, **409** для добавленного поля с тем же ID и **422** для нового некорректного запроса. Уверенность высокая: воспроизведено реальными маршрутами TestClient и SQLite.

### C2-2 — P2: позднее восстановление pending ID после reload

- Место: `web/workbench.js`, начальное `pendingOperation`, `syncActions` и завершающая инициализация после `await refreshCases()`.
- Триггер: в sessionStorage уже есть pending request, а начальный запрос истории задерживается. Пока сохранённый ID ещё не прочитан, reviewed-demo доступен и может начать новую операцию, заменяя сохранённый ID.
- Последствие: пользователь может потерять путь восстановления предыдущего запроса. Это не доказательство повторного платного вызова: новая reviewed-demo использует Reference. Проблема в сохранении идентичности незавершённой операции.
- Основание: прямая проверка порядка выполнения исходника; реальная браузерная задержка сети этим ревьюером не воспроизводилась. Уверенность высокая для порядка кода, средняя для частоты пользовательского проявления.
- Минимальная коррекция: синхронно восстановить только ID/kind до первого `syncActions`, не перезаписывать его позднее; дополнительно запретить `beginOperation` заменять существующую pending operation.
- Статус: **FIXED, повторно PASS на source/DOM-модели**. В текущем исходнике pending ID читается синхронно до handlers/awaits, поздняя перезапись удалена. `beginOperation` дополнительно отказывает при существующем pending. Независимый `node --test tests/test_studio.mjs tests/test_review_session.mjs` дал **11 PASS**, включая тест с незавершённым session-readiness promise, заблокированными execution controls и неизменённым исходным operation ID. Реальная браузерная задержка сети всё ещё **NOT_RUN** этим ревьюером.

## Что проверено в коде без заявления о runtime-проверке

- Operation rows сохраняют owner, ID, fingerprint и ссылки на результат; исходные тела и токены туда не записываются. TTL и количество ограничены. Поддержка рассчитана на один application worker; создание второго worker может ошибочно объявить чужую активную работу interrupted — это документированная граница, не подтверждённая multiworker-совместимость.
- Lock registry освобождает неактивные ключи и разделяет owner/case; optimistic revision остаётся после получения блокировки.
- CSV использует каноническую строку по binding, оставляет variance/price пустыми для исключений, явно передаёт причину и нейтрализует начальные формульные символы текстовых ячеек. В brief присутствуют quality warnings и оговорки об unsigned handoff.
- Новые OAT/residual формулы затрагивают только строки target, сохраняют остальные интервалы, используют Decimal. Формат исходных чисел допускает только целые quantities и цены до двух знаков; округление `span` не теряет дробных центов на этом домене.
- Лимит запросов в браузере теперь охватывает и чтение response body: 240 с исполнения, 60 с verifier, 20 с остальных запросов; автоматического повторного POST в этой функции нет. Отмена fetch не отменяет серверную работу, сообщение это объясняет. Реальную 240-секундную задержку ревьюер не воспроизводил.
