# Prooflane: независимое исследование улучшений, 8 ноября 2026

Авторская роль этого прохода — независимый исследователь и критик рекомендаций. Изучены текущие `README.md`, `WORKBENCH_CONTRACT.md`, `AGENT_RUSH_READINESS.md`, `reconciliation.py`, `case_api.py`, `case_store.py`, `store.py`, `workbench.js`, прежние дизайн-концепции и лицензии. Приложение и сервер этим исследователем не изменялись, браузерный сценарий и производительность не измерялись. Отдельный владелец реализации должен приложить фактические результаты. Соседние проекты не изучались.

**Вывод:** потенциал усиления есть в передаче результата другому сотруднику, разборе спорных источников, видимости пропущенного охвата и восстановлении после прерывания запроса. Полноценные AP-платформы уже предлагают matching, дубли, объяснения и audit trail. Поэтому эти слова сами по себе не доказывают отличие. Уместное позиционирование Prooflane — узкое дело о спорной цене, где решения о применённом источнике, их последствия и воспроизводимый пакет доступны отдельно от доверия к модели. Пользу этого подхода ещё нужно проверять на наблюдателях.

## Матрица возможностей: шесть направлений, по шесть независимых идей

Обозначения: **выбор** — рекомендация для ближайшей реализации, не заявление о выполнении. Сложность/риск: Н — низкие, С — средние, В — высокие для текущего Python/vanillaJS прототипа. Польза — гипотеза по найденной задаче, без пользовательских интервью. Связь с конкурсом: Т — Technology, П — Presentation, Б — Business Value, О — Originality. Один ID относится ровно к одному направлению. Ранее реализованный `priority_switch` не засчитывается как новое улучшение.

### A. Польза и функциональность

Исследование Dext и Ramp указывает на необходимость передачи результата в следующий рабочий шаг. Текущий пакет воспроизводим, но JSON не является удобной рабочей таблицей для сотрудника AP.

| ID и идея | Польза / связь с конкурсом | Сложность, риск | Критерий приёмки и отрицательный контроль |
|---|---|---|---|
| **A1 выбор: рабочая CSV-выгрузка** | Передать счета, source rows, договор, статус, количество и проверенное отклонение в рабочий процесс AP. Б/П | Н/С: CSV injection, precision | Каждая включённая/исключённая строка имеет явный статус; суммы сверяются с baseline; текст `=...` не выполняется как формула. |
| **A2 выбор: краткое дело для закупщика** | Самодостаточный human-readable brief: что проверить, исходная цена, охват, допущения, lineage и ограничения. Б/П | С/С: краткость может скрыть исключения | Brief отличает расчёт от рекомендации, содержит все исключения и ссылки/ID; нет выдуманного одобрения или возврата денег. |
| **A3 выбор: обзор общего договора** | Видеть всех потребителей одной ставки и суммарное отклонение, переходить к любой связанной записи. Б/П | С/С: смешение shared target и похожих IDs | Сумма группы равна сумме её реальных bindings; нулевые строки тоже видны; одинаковые invoice IDs не склеиваются. |
| A4 user-defined materiality filter | Сосредоточить список на пороге значимости без изменения исходных сумм. Б | Н/С: скрытие малых строк | Общее число/сумма и отфильтрованные строки подписаны; порог не влияет на export/receipt. |
| A5 отметка результата проверки человеком | Отделить рассчитано от проверено сотрудником. Б | В/В: нет identity/auth модели | Метка содержит имя, дату, причину и честный статус self-declared; не выдаётся за подпись. Лучше отложить до полноценной модели доступа. |
| A6 дополнительные единицы/валюты | Уменьшить реальные отказы загрузки. Б/Т | В/В: FX, дробные количества, новые формулы | Спецификация, справочник ставок и independent verifier меняются совместно; сейчас нет defensible данных — отложить. |

### B. Эффективность и производительность

В коде `reconcile` делает `_serialize` и `parse_csv` отдельно для каждого контракта и счёта. `list_cases` делает до 30 `store.get`, каждый открывает SQLite и выполняет prune. `Store` уже имеет индекс `(owner, created)` — повторное добавление такого индекса ничего не улучшает. Эти наблюдения объясняют кандидатов, но величина эффекта пока неизвестна.

| ID и идея | Польза / связь с конкурсом | Сложность, риск | Критерий приёмки и измерение |
|---|---|---|---|
| **B1 выбор: общие валидаторы полей вместо per-row CSV roundtrip** | Меньше работы при matching максимальных источников. Т/П | С/С: изменение принятого numeric domain | Старый/новый путь принимают и отвергают одинаковый набор входов; benchmark500+500, разогрев и несколько повторов, медиана и worst-case. |
| **B2 выбор: batch-проверка baseline IDs при истории** | Убрать N+1 connections/prune для архивных дел. Т | С/С: сессии/expiry | Одна сессия не видит чужие ID; 24h expiry одинаков; запросы и длительности для 0/1/30 дел до/после. |
| **B3 выбор: условный кеш только публичных assets** | Меньше переданных байтов при повторном открытии. П/Т | Н/С: stale release | CSS/JS/fonts дают 304 при валидном ETag, меняют ETag при изменении; HTML актуален; invoice JSON и packets не public-cacheable. Замерять bytes, не обещать вслепую wall-clock speedup. |
| B4 client-side maps для row/target lookup | Избежать многократных линейных поисков при 500 строках. Т | Н/С: stale lookup | Обновление maps при смене case; DOM/render benchmark до/после, исходные output неизменны. |
| B5 одно вычисление derived source per request | Убрать повторную parse/reconcile одного immutable baseline в rendering/evidence. Т | С/С: invalidation | Ключ cache зависит от raw sources+decisions+revision; session boundary сохранён; cost measured. Не вводить global unbounded invoice cache. |
| B6 bounded/lazy DOM rendering крупных списков | Быстрее initial paint длинного дела. П | С/В: доступность поиска/выделения | Все строки остаются достижимыми и экспортируемыми; keyboard/focus/screenreader и 500-row interaction measured. Только при обнаруженном узком месте. |

### C. Визуальный дизайн и взаимодействие

W3C tables/notifications дают правила контекста и состояний; Vic.ai подтверждает предметный инспектор. Существующая Audit Folio уже намеренно отличается от sidebar-dashboard. Не следует уничтожать полезную идентичность ради второго редизайна.

Три возможных направления: **Decision Desk** — компактный список решений с предметным правым полем; **Evidence Ledger** — доминирующий регистр с узкой колонкой аннотаций; **Comparison Stage** — сопоставление исходного и альтернативного результатов по общим строкам. Предпочтение — эволюция Decision Desk для Sources, сохранение Evidence Ledger для результата. Comparison Stage уместен только в разделе альтернатив, без переноса всей навигации.

| ID и идея | Польза / связь с конкурсом | Сложность, риск | Критерий приёмки |
|---|---|---|---|
| **C1 выбор: предметная композиция source decision desk** | Разделить очередной спор, исходные факты и действие; меньше конкурирующих заголовков. П/Б | С/С: потеря контекста | При первом входе видны количество нерешённых строк и выбранный спор; source→contract путь и выбранное решение читаются без цвета. |
| **C2 выбор: мобильное сравнение альтернатив** | Читаемое сравнение суммы, изменений и происхождения без вынужденного горизонтального чтения. П | С/С: дубли семантики | На 390/320px у каждого значения виден label; один accessible representation; все детали/скачивание доступны. |
| **C3 выбор: разные композиции empty/loading/error/result** | Состояние действия распознаётся по структуре и конкретному тексту; ошибка ведёт к исправлению. П | С/С: анимация скрывает состояние | Скриншоты всех состояний; status/alert, focus recovery и reduced motion не теряют сообщение. Это одна согласованная state-system, не четыре косметических пункта. |
| C4 типографическая шкала денежных сравнений | Упростить считывание baseline, delta и speculative range. П | Н/С: разные смысловые суммы выглядят одинаково | Явные подписи и единицы; tabular digits; min-font и contrast измерены. Не засчитывать одну замену font как новую функциональность. |
| C5 inline dependency path с таблицей-эквивалентом | Быстрее увидеть, что связано одним договором. О/П | С/С: граф-косметика | Подсвечивать только actual bindings; эквивалентный список, клавиатура и reduced motion. Приёмка по задаче, не количеству SVG. |
| C6 restrained semantic motion при смене выбранной записи | Объяснить изменение контекста инспектора. П | Н/С: vestibular/focus distraction | Короткий contextual transition только при `no-preference`; без layout shift и смены фокуса по завершению анимации. |

Предлагаемые tokens должны быть зафиксированы владельцем frontend: одна тёмная ink-основа для текста, muted paper, teal для действий/проверенного контекста, amber для нерешённого выбора; красный только для ошибки. Состояние всегда имеет текст. Не добавлять декоративные градиенты, одинаковые rounded cards и большие motion-сцены.

### D. Понятность и удобство

Исследование WAI указывает на конкретные инструкции и путь исправления. Наличие кнопки sample не означает, что зритель понимает задачу или сложные термины.

| ID и идея | Польза / связь с конкурсом | Сложность, риск | Критерий приёмки |
|---|---|---|---|
| **D1 выбор: точные скачиваемые CSV templates** | Пользователь начинает со схемы, которую сервер принимает. Б/П | Н/Н | Оба файла загружаются и проходят matcher; пример не выдаётся за реальные счета; headers совпадают со спецификацией. |
| **D2 выбор: first-use path с ролью и результатом** | За 30–60 с понять, что сотрудник AP проверяет против чего и что получит. Б/П | Н/С: рекламное обещание времени | Короткий entry copy, видимые 3 шага и sample; self-walkthrough from clean state, число действий и время наблюдения. Не называть user study. |
| **D3 выбор: переход к следующему нерешённому совпадению** | Убрать ручной поиск после решения и подсказать следующий chapter. Б/П | Н/С: автоматический переход скрывает результат | Решение подтверждено, есть явное Next unresolved; после последнего решения действие Create baseline; фокус стабилен, фильтр не ломает навигацию. |
| D4 field-linked CSV errors | Найти ошибочный record/field и исправить без гадания. Б | С/С: leaking unrelated data | Ошибка содержит file/record/field и допустимый формат, focus связан с редактором; raw secret data не попадают в log. |
| D5 пояснение цены, суммы отклонения и допущения у места действия | Уменьшить неверную интерпретацию savings/expected risk. Б/П | Н/Н | Новый пользователь может найти формулу и видит условие `not recovered savings`; tooltip не единственный путь. |
| D6 command palette/shortcuts | Ускорить повторную работу эксперта. П | С/С: новая незнакомая модель навигации | Все команды имеют видимые альтернативы, нет перехвата браузерных клавиш; отложить пока базовые шаги не ясны. |

### E. Инновации и конкурентные отличия

Здесь «инновация» означает полезную комбинацию/улучшение в текущем продукте, а не научную или мировую новизну. У каждой идеи есть короткий demo и проверка. Источник counterevidence: Ramp/AppZen уже выполняют matching и exception handling, MindBridge — объяснимые приоритеты. Следовательно, нельзя рекламировать эти категории как эксклюзивные.

| ID и идея | Проблема и отличие подхода / конкурс | Сложность, риск | Короткий demo и критерий |
|---|---|---|---|
| **E1 выбор: последствия каждого допустимого спорного договора до выбора** | В обычном matching требуется выбрать вариант; здесь цена каждого eligible источника сразу даёт прослеживаемое следствие для данной записи. О/Б | С/С: сравнительную сумму принять за рекомендованный договор | На INV504 показать оба источника и 40/32 отклонения, не выбирать автоматически. Independent Decimal oracle, даты и eligibility, подмена кандидата отвергается. При полном сравнении дела нужно явно определить, какие decisions изменяются. |
| **E2 выбор: диагностика повторяющихся исходных строк** | Дубль может раздуть результат, но повтор invoice ID может быть законной строкой. Прозрачный сигнал показывает exact-repeat и repeated-ID отдельно. Б/О | С/С: false fraud label | Создать повтор fixture, увидеть связанные source rows и предупреждение; ни одна строка не исчезает молча; legitimate line items не называются доказанным дублем оплаты. |
| **E3 выбор: денежный слепой участок исключений** | Счёт вне расчёта может выглядеть как нулевой риск. Считать только billed amount исключённых источников, отдельно от неизвестного variance. Б/О | С/С: сумму счёта спутать с overcharge | На INV506 показать 250 billed outside scope и объяснение «variance not calculated». Проверить included+excluded billed coverage, нули/границы/многократные ID; не складывать её с 768 variance. |
| E4 constrained review-intent compiler | Перевод вопроса аудитора в разрешённые targets/changes с явным preview; не chat ради chat. О/Т | В/В: additional provider calls, invalid IDs | «Если C1 станет 80?» → предложенный typed draft → explicit apply; held-out tests, отказ от unsupported вопроса, model provenance. Отложить без измерения качества и лимита бюджета. |
| E5 verifier challenge mode | Показывать original packet и одну семантическую подмену с тем же пересчитанным hash. О/Т/П | С/С: зритель спутает tamper fixture с атакой | Offline original passes; rehashed false claim fails. Это улучшение объяснения уже существующего verifier, не новая crypto protection. |
| E6 evidence sufficiency checklist для конкретного price boundary | Запросить ровно то подтверждение, которое способно изменить текущий приоритет. О/Б | С/С: boilerplate как псевдо-интеллект | Ссылка на actual contract ID, affected rows и exact boundary; missing/tied states; не обещает получить документ и не выдумывает evidence. |

### F. Надёжность и готовность демонстрации

Исторические доказательства фиксируют сохранённый сервером live result при клиентском timeout. В текущем `api()` не видно AbortController/request deadline; state хранится только в памяти. Это конкретные risks, без необходимости в новых облачных ресурсах.

| ID и идея | Польза / связь с конкурсом | Сложность, риск | Критерий приёмки |
|---|---|---|---|
| **F1 выбор: operation ID и получение результата после потерянного ответа** | Не платить/не исполнять повторно только потому, что ответ потерялся. Т/П | В/В: concurrent mutations и ownership | Прервать ответ после принятия, восстановить по той же сессии; повтор того же ID не создаёт новый run; другое тело конфликтует, чужая сессия не читает. Не превращать timeout в auto-retry POST. |
| **F2 выбор: восстановление открытого дела и chapter после reload** | Законченный обзор не исчезает с экрана при обновлении. П | Н/С: expired/foreign IDs | Хранить только owned case ID/chapter, не CSV/token в localStorage; сервер повторно проверяет ownership и TTL; expired показывает осмысленный recovery. |
| **F3 выбор: ограничение ожидания и безопасный путь восстановления** | UI не зависает навсегда при недоступности сервера. П/Т | С/С: abort не отменяет сервер | Тест зависшего fetch/неполного JSON, busy finally, сообщение про неопределённый результат, проверка operation status вместо повторного выполнения. |
| F4 draft-change guard | Не потерять несохранённые допущения при New review/Archive. Б/П | Н/С: modal fatigue | Предупреждать только при реальном draft; stay/discard keyboard; токены не сохранять; frozen baseline не мутирует. |
| F5 экспорт при истечении дела | Заранее объяснить 24h retention и скачивание packet; дать local verification без online case. П | Н/Н | После удаления/expiry старый downloaded packet проверяется; UI не обещает вечный archive; ошибки экспорта различают недоступность и invalid artifact. |
| F6 clean-checkout rehearsal | Не зависеть от локальных caches для setup. Т/П | С/С: отсутствующий Git remote | Новый отдельный каталог/venv без переноса .env, lock install, reference startup, sample HTTP. Docker и real provider gates отдельно; не выдавать existing venv за clean setup. |

## Самые сильные возражения и пересмотр уверенности

1. **Модель решает тривиальную проверяемую формулу.** Это честно демонстрирует containment, но не доказывает аналитическую пользу LLM. E4 мог бы улучшить роль модели, однако требует данных/оценки и новых вызовов; риск срыва выше. Текущие детерминированные улучшения усиливают продукт, а не скрывают этот предел.
2. **18 новых изменений за один цикл могут ухудшить стабильность.** Матрица не предписание внедрить всё. Выбранные 3×6 нужно подтверждать как отдельные пользовательские поведения. Если измерения опровергнут B3 либо UI покажет C1 уже решённым, заменить или честно обосновать отказ. Косметические подпункты одного компонента не закрывают квоту.
3. **Диагностика дублей и coverage не уникальны.** Рекомендация основана на полезности и сохранении прозрачности, не на монополии идеи. Сильнее демонстрировать связанную цепочку source ambiguity→counterfactual→handoff→offline rejection.
4. **Гарантировать бизнес-эффект пока нельзя.** Нет интервью, реальных бухгалтерских данных и замеров новой аудитории. Уверенность в корректной применимости к toy formula высокая, в переносе на реальный AP workflow — средняя/низкая до наблюдений.
5. **Скорость сервера может доминироваться сетью/LLM, а не parser.** Локальное улучшение CPU при 500 строках не следует переводить в «сайт в N раз быстрее». Метрики отдельно: function CPU, bytes/conditional loads, query count, human actions, real provider latency.

Минимальный эксперимент после выпуска: дать двум наблюдателям один синтетический спор с C1 и C2R, предложить сначала таблицу, затем Prooflane с перестановкой порядка между людьми. Задачи — указать affected invoice rows, обосновать exclusion, назвать цену смены приоритета и передать воспроизводимый результат. Записывать время, правильность и место затруднения. Малый набор даёт только описательный сигнал; непройденное исследование обозначать NOT_RUN.

## Правила подтверждения после реализации

Владелец реализации должен добавить отдельную таблицу «ID→файлы→проверка→результат», исходные/итоговые скриншоты, сопоставимые perf fixtures, фактические source-to-result прогоны и два независимых критических цикла. Этот документ не является свидетельством выполненного кода, принятой конкурсной заявки, живой новой AI-интеграции или аудита безопасности. Все рекомендации помещаются в существующий стек и бюджет; платные сервисы/расширение доступа не нужны. Для придуманного экземпляра данных обязательна видимая synthetic маркировка.
