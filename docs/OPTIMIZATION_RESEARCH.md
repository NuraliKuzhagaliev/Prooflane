# Prooflane: проверка направления оптимизации

Дата проверки источников: **2026-11-03**. Решение: стоит ли развивать существующий анализ расхождений в ценах в сценарий **«оспорить одно допущение, повторно выполнить расчёт и передать проверяемое сравнение»**. Это исследовательский отчёт, а не подтверждение готовности новой функции. Срез исходного состояния: commit `c2a3662`; параллельные изменения команды не входят в начальную оценку.

## Вывод

**Рекомендация, уверенность средняя:** реализовать один ограниченный сценарий изменения исходного допущения с неизменяемым исходным результатом, повторным запуском существующего pipeline и пакетом двух квитанций. Дополнить его тремя согласованными возможностями: точной привязкой изменений к исходной записи, независимой проверкой сравнения и понятным пошаговым интерфейсом на узком экране. Это увеличивает полезное поведение продукта без новой инфраструктуры, модели или формата импорта.

Гипотеза ценности: проверяющему легче разобраться, почему изменилась сумма, если он видит исходные значения, одно явно заявленное изменение и воспроизводимую разницу. Интервью, продажи и сравнительные пользовательские испытания отсутствуют. Нет оснований называть это новым классом аналитики, доказанной экономией времени или преимуществом над всеми конкурентами.

Самое сильное возражение: обычная таблица уже позволяет менять цену и пересчитывать формулу. Prooflane должен выиграть удобством **проверки и передачи двух согласованных состояний**, а не самим what-if расчётом. Второе возражение: эта функция сама по себе не делает необходимой генерацию кода моделью для заранее известной формулы.

## Границы доказательств

- **verified:** непосредственно прочитанный код, локальный артефакт либо содержание первичного источника. Для страницы поставщика подтверждается его публичное заявление, а не точность продукта.
- **hypothesis:** проверяемое предположение о пользе, UX или поведении пользователя.
- **opinion:** аналитическая оценка приоритета или силы демонстрации.
- **recommendation:** предложенное действие с условиями приёмки.

Конкуренты не устанавливались, их платные аккаунты не открывались и одинаковые CSV на них не запускались. Цены, latency, вероятность ошибок, полнота функций и безопасность между продуктами не измерялись. Отсутствие функции на изученной странице означает **UNKNOWN**, а не «у конкурента этого нет». Локальные результаты ниже прочитаны из артефактов предыдущего запуска, а не заново воспроизведены этим исследователем.

## Научные предпосылки, а не доказательство новизны

- [PAL: Program-aided Language Models](https://arxiv.org/abs/2211.10435), первая версия 2022-11-18, просмотренная v2 — 2023-01-27. Публикация исследует генерацию программ как промежуточное представление с выполнением интерпретатором. Это прецедент архитектуры, а не свидетельство точности нашего агента.
- [Program of Thoughts Prompting](https://arxiv.org/abs/2211.12588), первая версия 2022-11-22, просмотренная v4 — 2023-10-23. Авторы отделяют языковое рассуждение от вычисления и рассматривают, в том числе, финансовые QA-задачи. Их benchmark нельзя переносить на наши CSV, модель, данные или deployment.

Таким образом, code execution, проверяемая арифметика и объяснимость по исходным данным — известные строительные блоки. Возможный вклад Prooflane — их аккуратная интеграция в конкретный сценарий проверки изменённого допущения. Сравнительная научная новизна не установлена.

## Самые сильные возражения к выбранному флагману

1. **Изменение допущения может выглядеть как доказанное исправление счёта.** Новый contract_price — введённое пользователем предположение. Оно не удостоверяет договор и не создаёт юридического требования. Термины scenario / assumption / variance обязательны; «recovered savings» недопустимо.
2. **Хеширование создаёт ложное доверие.** Злоумышленник может изменить CSV, код, metadata и пересчитать хеши. Проверка должна отдельно подтвердить арифметику и заявленное единственное изменение; происхождение издателя и runtime остаются неподтверждёнными.
3. **Флагман не устраняет избыточность AI.** Для одного детерминированного расчёта модель не нужна. Честная демонстрация ценности — контроль результатов исполняемого агента, когда модель реально подключена; reference остаётся самостоятельным полезным режимом.
4. **Чужие/несвязанные результаты легко выдать за comparison.** Bundle должен связывать baseline/scenario, проверять одинаковое число и порядок записей, ровно одно разрешённое изменение и неизменность всех остальных полей. Межсессионное сравнение через API запрещено.
5. **Record identity хрупка.** Invoice IDs могут повторяться, CSV-поле notes может содержать переносы строк. Идентичность в текущем scope — порядковая запись после parsing; это надо показывать и проверять.
6. **Новая точка отказа удваивает исполнение.** Сценарий не должен скрыто подменять недоступный sandbox host-расчётом или превращать таймаут в успешный результат. При провале baseline остаётся доступен, scenario помечен неуспешным.
7. **UX может стать сложнее Excel.** Если для понимания изменения пользователю приходится изучать JSON и Docker, ценность проиграна. Evidence доступен по мере необходимости; сначала простое before/after.

## Минимальный эксперимент, способный отменить решение

**До заявления о пользе:** два независимых проверяющих, одинаковый синтетический CSV и две задачи: объяснить исходное расхождение и проверить одно изменение цены. Один начинает с прежнего интерфейса/копии таблицы, другой — с нового; затем поменять порядок на другом эквивалентном наборе. Это маленькая formative проверка, не статистический benchmark.

Зафиксировать без выдуманных чисел: правильность суммы и причины изменения, возможность найти исходную запись, сохранён ли baseline, может ли второй человек проверить переданный пакет без живого сервера, ошибки и фактическое время. Не направлять участника к нужной кнопке. Критерий пересмотра: пользователь принимает сценарий за подтверждённый договор/экономию, не объясняет delta, не находит оригинал либо обходится старой таблицей проще. В этом случае упростить flow или отказаться от заявления о преимуществе.

**Инженерная приёмка до пользовательского опыта:** базовый пример 1480.00; у record 3 contract_price 72.00 → 80.00 при quantity 40 даёт scenario 1160.00 и delta −320.00. Это ожидаемый расчёт, не результат ещё не выполненного нового запуска. Проверить также появление/исчезновение finding, отсутствие влияния на billed при изменении только contract_price, quantity/price bounds, дубликаты ID, quoted multiline, большие суммы, потерю baseline, чужую сессию, остановку Docker и модифицированный bundle с заново рассчитанным внешним hash.
