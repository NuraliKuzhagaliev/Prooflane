# Границы безопасности

Prooflane — ограниченный hackathon-прототип. Локальная проверка нескольких ограничений не является аудитом всей инфраструктуры или сертификацией безопасного исполнения любого кода.

## Модель угроз

Недоверенные входы: CSV/имя файла/вопрос пользователя, план и код модели, stdout/stderr контейнера. Защищаем: серверные ключи VSI, host filesystem, результаты других браузерных сессий, доступность и бюджет. Доверяем текущему серверному коду, host OS, Docker daemon, закреплённому base image и администратору VM.

## Реализованные меры

- Generated Python исполняется только через отдельный Docker container. Executor не принимает пользовательские shell arguments, image, mounts или runtime flags. Вход идёт через stdin, а не host mount.
- Контроль перед стартом: inspect подтверждает network none, readonly root, UID/GID 65534, память 128 MiB, swap cap, 0.5 CPU, 32 PID, cap-drop ALL, no-new-privileges и отсутствие host mounts. tmpfs ограничен 16 MiB.
- Тайм-аут, пределы stdout/stderr и проверенный cleanup ограничивают runaway задачи. Если cleanup не подтверждён, результат отклоняется и сохраняется `sandbox-quarantine.json`; новые sandbox-задачи блокируются. При readiness-проверке нового процесса контейнеры с label `prooflane.sandbox=true` также включают карантин. Marker переживает restart; оператор должен проверить оставшиеся контейнеры.
- VSI credentials находятся на сервере; URL фиксирован, redirects и proxy environment в HTTP client отключены. API-ключ не передаётся sandbox или браузеру. Live calls отключены по умолчанию и требуют отдельного operator token.
- CSV schema/size/ranges проверяются до запуска. Output сверяется с отдельным Decimal oracle целиком. Непроверенные числовые результаты не публикуются как verified.
- Runs привязаны к случайной HttpOnly/SameSite session cookie. HTTPS делает cookie Secure. POST проверяет Origin, JSON и custom header. API имеет bounded concurrency и in-memory quotas; CSP и security headers ограничивают браузерный контекст.
- Сценарий использует оригинал той же сессии, его hash и исходный режим; менять можно только одно числовое поле. Экспорт проверяет владение обеими версиями. Offline verifier пересчитывает полный набор записей и отклоняет незаявленные изменения даже при валидных отдельных receipt и пересчитанном внешнем hash. Это проверка согласованности, не подпись отправителя или аттестация runtime.
- Новый case workbench использует те же session/run/provider границы. Два файла сопоставляются только по точным ключам и датам; неоднозначности не разрешаются автоматически. До4вариантов по12distinct targets наследуют original execution mode; общая цена применяется ко всем связанным счетам. Revision CAS и один процессный lock предотвращают потерю одновременных правок. Failed run не становится вариантом. Cases ограничены200записями и24часами; они не продлевают срок baseline run.
- Case packet проверяет обе исходные таблицы, явный scope, baseline case context, полное распространение изменений, все receipts и точную аналитику. Browser/CLI verifier принимает до8MiB и не исполняет/не импортирует пакет. Create/match body до2MiB, каждый source до128KiB, не более5,000 matching links; прочие операции сохраняют предел180KB. Case operations имеют отдельные in-memory quotas. Это меры ограничения объёма, не результат публичного load test.
- Некорректная оболочка provider response и невалидный Unicode в plan/code/model отвергаются до исполнения. Repair после ошибки исполнения возможен только при подтверждённом cleanup; raw CSV и stderr не добавляются в feedback модели.

Реальная локальная проверка: `artifacts/sandbox-smoke.json`; сценарии и отрицательные проверки — `artifacts/optimization/` и `artifacts/optimization-review/`. Текущие счётчики тестов и их границы в [TESTING](TESTING.md), включая failure/restart/orphan gates и retry-contract с doubles. Настоящий SIGKILL процесса и реальный VSI **NOT_RUN**; passing tests не заменяют эти эксперименты. Проба сетевого соединения с documentation IP доказывает конкретный отказ вместе с подтверждённым network-none config, а не универсальное отсутствие каналов утечки. Проба env проверяет отсутствие переменной VSI, не сканирует и не доказывает отсутствие всех возможных секретов.

## Существенные остаточные риски

Docker использует ядро хоста. Уязвимость ядра/daemon или ошибка параметров может разрушить границу. Backend имеет доступ к daemon; членство в `docker` даёт root-level полномочия, даже если process user не root. Установка systemd `NoNewPrivileges` не устраняет этот доступ. Поэтому использовать только выделенную VM без других рабочих нагрузок и не публиковать daemon TCP API. [Docker post-install](https://docs.docker.com/engine/install/linux-postinstall/), [Docker security](https://docs.docker.com/engine/security/).

Operator token — общий секрет для демонстрации, не полноценная RBAC/account система. Его получение позволит расходовать доступную квоту live. Rate limits сбрасываются при рестарте; лимиты живут в одном worker и не заменяют биллинговый cap. Общедоступные sandbox-запросы могут создавать нагрузку. Перед широким доступом нужны host-level quotas/monitoring и review.

SQLite и receipt содержат исходный CSV. Строки старше 24h удаляются при add/get/list, без фонового точного таймера. Свободные страницы/backup могут хранить байты: secure wipe не реализован. Шифрование data at rest самим приложением не реализовано. Для demo допускаются только несекретные/синтетические данные. Не отправлять receipt третьим лицам без проверки содержимого.

SHA-256 receipt не подписан. Можно изменить все поля и пересчитать хеши. Offline verifier проверяет внутреннюю согласованность и фиксированную арифметику, но не личность автора, существование sandbox execution, истинность CSV или бизнес-правомерность вывода.

Текст вопроса передаётся VSI. Хотя сырые строки CSV не отправляются автоматически, пользователь может сам вставить данные в вопрос. Prompt instructions не считаются sandbox boundary; проверяется результат и применяются OS-level ограничения.

## Эксплуатация

Хранить `.env` вне Git с ограниченными правами; не печатать его и не включать в support logs, скриншоты или видео. При утечке отозвать ключ на стороне Vultr и заменить operator token. Проверить доступные host updates перед публичным deployment. HTTPS и ограничение доступа к SSH настраивает владелец VM; не выставлять Uvicorn на публичный интерфейс.

При cleanup failure или orphan gate приложение уже блокирует новые sandbox-задачи. Остановить сервис, проверить `docker ps -a --filter label=prooflane.sandbox=true`, сопоставить каждый exact container ID с marker/логом и инспектировать его. Установить причину, затем удалить только подтверждённые leftover containers этого проекта. Лишь после подтверждения отсутствия этих контейнеров и устранения причины удалить конкретный `PROOFLANE_DATA_DIR/sandbox-quarantine.json` и перезапустить сервис. Не снимать marker ради обхода ошибки. Не применять `docker system prune` или массовое удаление чужих контейнеров. При инциденте сохранить несекретные идентификаторы/логи, выключить live, ограничить доступ, затем воспроизвести проблему на синтетических данных.

Для сообщения о дефекте предоставить шаги, версию, синтетический reproducer и фактический результат; не добавлять credentials или реальные счета. Контакт/security advisory URL появится после выбора публичного репозитория. Механизм bug bounty не заявлен.
